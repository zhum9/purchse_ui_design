# 采购执行中心：金仓建库脚本

适用基线：KingbaseES V8，Oracle 兼容模式；核心版 V1.1。所有表统一使用 `pur_` 前缀，**不设置物理外键，不做级联删除**。

## 1 文件与执行顺序

| 文件 | 用途 |
| --- | --- |
| [001_pur_core_schema.sql](001_pur_core_schema.sql) | 一次性初始化：45 张表、1 个统一技术 ID 序列、主键、36 个唯一约束、178 个 CHECK 约束、99 个普通索引及全部字段中文注释 |
| [数据库设计](../../docs/PROCUREMENT_CORE_DATABASE_DESIGN.md) | 字段含义、逻辑关系、状态、事务、查询与迁移边界 |
| [UI 设计](../../docs/PROCUREMENT_CORE_UI_DESIGN.md) | 页面、操作、校验及后续验收场景 |

目前只有一个需要执行的 SQL 文件，不需要先执行其他业务脚本。没有供应商确认专用表、回复状态或回签门槛。

这是初建结构，**不是旧库升级脚本**。已有数据库如需迁移，必须另外评审字段映射和数据迁移脚本，不能直接用本脚本覆盖。

## 2 执行前

1. 由 DBA 确认目标确为 V8 Oracle 模式，记录具体 R 版本、补丁和驱动；不需要改变兼容模式或重新初始化实例。
2. 新建或选择一个专用的空 schema；确认当前会话的目标 schema，不在含已有采购数据的 schema 中执行。
3. 确认执行账号拥有在该 schema 创建表、序列、索引和添加注释的权限。脚本不创建账号、不写密码、不授予全库权限。
4. 使用 UTF-8 打开脚本，在管理工具中将“遇到错误继续执行”关闭。不要跳过失败语句，也不要重复运行来补齐未知的半成品。
5. 首次在隔离库核验类型、字符长度、CLOB 读写、CHECK、序列和驱动绑定；之后按企业发布流程建正式库。

本文不声称已在你的实例实跑成功。此次只交付脚本和静态结构核对，不连接、创建或修改用户数据库。

## 3 执行与失败处理

在已确认的 schema 下执行整个 `001_pur_core_schema.sql`。脚本先创建统一序列，再依次创建各表、注释和普通索引；由于不使用外键，不存在建表之间的物理依赖。

脚本没有 `DROP`、`TRUNCATE`、业务数据 `DELETE` 或 `CREATE TABLE IF NOT EXISTS`。对象已存在应作为错误停止，不能把“跳过已有对象”误认为结构已一致。脚本也不会自动设置当前 schema 或覆盖已有对象。

如果中途失败，保存错误和已完成对象清单，由 DBA 判断失败原因及是否更换新的空 schema。**不附自动清库回滚脚本**，也不假设所有 DDL 在所有补丁/客户端下都能整体回滚。

执行后核对表、约束、索引、注释清单与本文件数量；物理外键数量应为 0。是否成功以目标实例的实际执行结果为准。

## 4 ID、时间和字段类型

- 技术 ID 使用 `NUMBER(19,0)`，范围限制为正有符号 64 位整数；所有逻辑关联 ID 同类型。API 中以字符串返回 ID 和十进制数。
- 已提供 `pur_core_id_seq`。应用可显式取序列值后插入，例如金仓文档中的 `SELECT NEXTVAL('pur_core_id_seq');`；实际 ORM 的取号语法按目标驱动核验。所有独立主键表共用同一方案。
- 表字段不绑定隐式自增或序列默认值，允许企业统一 ID 服务替代；一旦选择必须统一，不能在同一 ID 空间随意混用，禁止 `MAX(id)+1`。导入保留旧 ID 时需专门评审碰撞与序列水位。
- `revision_id` 为主键的头表复用版本 ID；行内容表复用 `(revision_id,line_id)`，不能给这类关联键另取无关的新 ID。
- 序列回滚、缓存、并发造成断号是正常现象；业务单号由编号服务生成，不要求技术 ID 连续。
- `TIMESTAMP(6)` 由应用显式写 UTC；`DATE` 字段按业务时区归一到自然日零时，不能假设 Oracle 模式 DATE 不含时间。审计时间不依赖数据库会话的本地时间默认值。
- 金额/数量是 `NUMBER`，字符串为 `VARCHAR2(n CHAR)`，逻辑 JSON 为 `CLOB`。应用校验 JSON 结构、长度、敏感内容和金额舍入；不依赖 JSONB 扩展。
- 草稿商业字段允许 NULL，不填假供应商、0 元或占位日期。主键、核心身份、状态和审计字段不可空；提交完整性由业务服务按场景检查。

## 5 无外键情况下的后端责任

DDL 保留主键、唯一约束、NOT NULL、布尔/枚举/数值/部分行内 CHECK，但它们不会保证表间关联正确。不能把“插入未报错”作为业务校验通过。

至少在同一业务事务内完成：

1. 核验单据、版本、稳定行、法人、组织、供应商、单位及来源 ID 存在且适用；版本和行必须属于同一单据，目录还需验证类型。
2. 校验所有输入主体的数据权限，防止跨法人/跨部门引用。前端传来的 readonly 字段仍须重新读取或校验。
3. 按固定顺序锁单据根及相关稳定行，读取最新来源占用/承诺和履约事实，再写事件。删除、导入、后台修复也必须遵循相同协议，避免校验后对象被移除。
4. 版本提交冻结业务内容；正式分配事件、履约事件、归属记录、审计和证据不得覆盖或硬删除。DDL 不使用触发器模拟外键或完整状态机。
5. 校验跨行分配合计、服务/限额控制、行金额与币种、交付总量及反向原单范围；一条 CHECK 不能完成这些跨表规则。
6. 幂等命令、业务写入及集成任务必须同事务提交；SAP 调用在事务外。UNKNOWN 必须先核对，唯一请求键不能单独保证外部绝对不重复执行。
7. 正式数据原则上不物理删除。草稿清理也要先检查版本、来源、附件、任务等逻辑引用；不允许绕开业务服务任意改关联 ID。
8. 建立周期性的孤立引用和余额一致性核查；发现异常阻断相关业务并人工核对，不能自动删除孤立记录或伪造补齐业务事实。

参考用户、组织、规则等基础目录须经正式初始化或外部同步提供。脚本不插入虚构用户或演示业务，不替代 IAM、审批规则发布与 SAP 适配实现。

## 6 本轮范围及评审状态

- 供应商确认流程、发送/回复专用表和确认准入均已移出本期。
- 订单数量、约定交期、分批地点仍用 `pur_order_schedule`；净履约与关闭量用于计算未交和逾期。
- 可选内部预计及延期备注追加到 `pur_audit_event`，附件关联该记录；不得覆盖正式交期或生成额外履约占用。
- 45 张表中包含组织、权限、附件等可复用支撑表。企业已有公共平台时，先确认复用映射，再裁剪初始化范围，不能运行后直接删除关联表。
- 本轮已经确认表前缀和无外键要求；其余正式 PO 权威、审批归属和 SAP 反向粒度仍按设计文档的评审边界处理。
